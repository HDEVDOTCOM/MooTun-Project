## Scope

- Phase 1D = require explicit confirmation before deleting the latest
  transaction.
- Phase 1E = undo deletion, deferred.
- Phase 1D adds no undo/snapshot fields. No restore history is stored.

---

## PendingAction Schema

- One `PendingAction` per LINE user (PK `line_user_id`).
- Immutable `action_id` (32-char hex, `uuid4().hex`).
- Integer `version` (OCC guard; `version > 0`).
- `action_type` = `confirm_delete`.
- Exact `target_transaction_id` (bound at creation; never re-derived).
- `created_at` (immutable).
- `expires_at` (fixed TTL).
- Fixed TTL = **10 minutes** (`PENDING_ACTION_TTL = timedelta(minutes=10)`).

---

## Coexistence

- A `PendingAction` and a `PendingTransaction` may exist for the same user at
  the same time.
- Neither implicitly destroys the other. A delete confirmation does not cancel,
  replace, or mutate an entry draft, and an entry draft does not cancel a
  confirmation.

---

## PendingAction Read Contract

Semantic result states:

- `ACTIVE(action)` — an unexpired action.
- `EXPIRED_CLEANED` — an expired action existed and was removed by this read.
- `ABSENT` — no action existed.

Implementation mapping:

- `repository.PendingActionState` with members `ACTIVE`, `EXPIRED_CLEANED`,
  `ABSENT`.
- `repository.PendingActionResult` with fields `state` and `action`.
- `repository.get_pending_action(...)` returns a `PendingActionResult`.

Do not treat `ActionStateKind` / `.kind` as the canonical names; those appear only
in the pre-implementation review text. The actual code uses `PendingActionState`
and `PendingActionResult.state`.

---

## Routing: `ยกเลิก`

Evaluated before any `PendingTransaction` read for control words.

- `ACTIVE(confirm_delete)` -> cancel the `PendingAction` only; preserve
  `PendingTransaction`. Reply: `ยกเลิกการลบแล้ว`.
- `EXPIRED_CLEANED` -> reply that the delete confirmation expired
  (`คำสั่งลบหมดอายุแล้ว กรุณาส่ง 'ลบล่าสุด' อีกครั้งหากต้องการลบ`); preserve
  `PendingTransaction`; stop routing for this webhook event.
- `ABSENT` + active `PendingTransaction` -> existing Phase 1B draft cancellation.
- `ABSENT` + no `PendingTransaction` -> preserve pre-Phase-1D fallback behavior.

---

## Routing: `ยืนยัน`

- `ACTIVE(confirm_delete)` -> confirm the exact stored target (see Atomic
  Confirmation).
- `EXPIRED_CLEANED` -> expiry reply; delete nothing; preserve `PendingTransaction`;
  stop routing.
- `ABSENT` -> existing unresolved/unknown behavior.

---

## Other Commands

- Unrelated commands may treat `EXPIRED_CLEANED` as absent and continue normally,
  so a user is not forced to acknowledge an expired state before acting.
- Stateless commands (help, recent, monthly summary, savings status) preserve an
  active `confirm_delete` and do not refresh its `expires_at` or `version`.
- State-mutating transaction commands (new transaction, successful Phase 1B
  completion, edit-latest, repeated `ลบล่าสุด`) must invalidate an observed active
  `confirm_delete` via OCC before their primary business mutation.

---

## Latest Target

- "Latest" = most recently recorded: `created_at DESC, id DESC`.
- The `target_transaction_id` is fixed when the confirmation is created.
- A confirmation never re-queries latest and switches targets.

---

## Atomic Confirmation

- Conditionally consume the exact `PendingAction` (identity + version + type +
  target + unexpired).
- Delete the transaction by **both** `target_transaction_id` and `line_user_id`.
- Both steps occur in one outer transaction.
- A missing target safely cleans up the exact action and returns
  `ไม่พบรายการที่ต้องการลบ (อาจถูกลบไปแล้ว)`.
- `PendingTransaction` remains untouched throughout.

---

## OCC / Race Model

- Mutations predicate on `line_user_id` + `action_id` + `version` + unexpired
  status.
- Lazy-expiry cleanup is OCC-safe (conditional on the exact observed identity,
  version, and expiry).
- If expired A1 is replaced by A2 and the cleanup DELETE loses:
  - deterministic retry reply;
  - no reinterpretation against A2;
  - no draft mutation;
  - loser reply cached in `ProcessedWebhookEvent`.
- An invalidation OCC loser performs no business mutation (no transaction, no
  edit, no draft completion).
- Repeated `ลบล่าสุด` replacement follows the same OCC rules (invalidate exact
  old action, then create a fresh confirmation for the current latest).
- No claim of global per-user serialization. The confirmation is permanently
  bound to one transaction id, and every deletion is strictly user-scoped and
  atomic.

## Confirmation Prompt

Must identify the exact target with:

- income/expense type,
- description,
- amount,
- category,
- B.E. date.

Implemented by `messages.format_delete_confirmation_prompt`, which reuses the
existing amount/category/date helpers and B.E. formatting.

---

## Phase 1E Guardrails

Do not add these fields in Phase 1D. The future undo snapshot must be captured
atomically at confirmed deletion time and preserve at least:

- `original_transaction_id`
- `line_user_id`
- `transaction_type`
- `amount_satang`
- `category`
- `description`
- `occurred_on`
- `created_at`

Phase 1E must separately decide restore identity/order semantics (reuse original
id vs. new id plus ordering logic).
